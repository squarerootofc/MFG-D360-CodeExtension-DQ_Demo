Contact data quality
with a Data 360 code extension

How a tested, versioned Python script turns 30,000 messy contacts from three systems into 18,000 correctly resolved people, with no false merges.

🔥 Fire ❄️ HVAC 🔒 Security

Demo company: Acme Building Technologies (ABT). It is fictional, and every name, domain and number in this deck is a placeholder.

The problem

One facility manager. Three systems. Three spellings.

ABT sells fire, HVAC and security equipment through two direct CRMs and a dealer network. The same person is often entered more than once, and typed differently each time (illustrative):

CRM_NA           raj.patel@ironbridge-demo.com
CRM_EMEA          Raj.Patel@IronBridge-Demo.com 
DEALER_PORTAL    Raj Patel <raj.patel@ironbridge-demo.com>

Meanwhile, hundreds of unrelated people share one placeholder:

noemail@example.com   ← 630 contacts, all three sources

What that costs the business

  • Missed matches. The same customer is treated as two or three people.
  • False merges. Strangers who share noemail@example.com are fused into one "person". That's a compliance problem, not just a cosmetic one.
  • Unusable contact points. Phones that say see notes and countries that say Atlantis.
  • No audit trail. Nobody can say which rules produced which value.
The approach

What a code extension is

Your own Python (PySpark) script, deployed into Data 360 and run on Data 360 compute through a batch data transform.

🧪 Testable

The rules are plain functions, so you can unit-test them on a laptop against all 30,000 rows with no org and no credits.

🏷️ Versioned

Each deploy has a --package-version, and every output row carries a rule_version__c. You always know which rules made a value.

🚚 Promotable

The extension moves to the next org inside a DevOps data kit, together with its batch data transform. Nothing is rebuilt by hand.

It reads and writes like a SQL transform: DLO → DLO or DMO → DMO. What's different is that the rules are real code, kept in version control, with tests.

Inside the script

Rules in plain functions. The SDK only in main().

def transform(raw):
    df = raw.select("contact_id__c", "source_system__c",
                    "product_line__c", "email__c",
                    "phone__c", "country__c")
    df = _email(df)      # status + email_clean__c
    df = _phone(df)      # status + phone_clean__c
    df = _country(df)    # status + country_iso2__c
    return add_key_and_hash(df)

def main():
    client = Client()
    result = transform(client.read_dlo("ABT_Contact_Raw__dll"))
    client.write_to_dlo("ABT_Contact_DQ__dll", result,
                        write_mode=WriteMode.OVERWRITE)
  • transform() is pure PySpark, so tests call it directly on the CSV. No org is involved.
  • Lowercase every column name. Data 360 resolves script columns in lowercase; Email__c fails with column does not exist.
  • Spark built-ins only. No UDFs, RDDs, SparkContext patterns or listeners.
  • Same object type in and out. This demo goes DLO → DLO.
The script is simplified here. The full version is code_extension/payload/entrypoint.py.
Change detection

The DQ hash: proof that the rules reached every row

dq_hash__c = SHA-256( rule_version | source_system | contact_id | email | phone | country )
                       blanks coalesced to '' first, so the hash is never null

One record changes

Exactly one hash changes. Downstream jobs re-sync, re-activate or re-score only that row.

A rule changes

Bump RULE_VERSION and every hash changes. One GROUP BY rule_version__c proves the new rules hit all 30,000 rows.

What it doesn't do

It saves downstream work. The extension's own run still reads every row, so the hash doesn't make the run itself cheaper.

Write modes

OVERWRITE today, MERGE when it grows

ModeWhat it doesUse when
OVERWRITEReplaces the whole targetFull refresh. The simplest option, and what this demo uses
APPENDAdds rowsRun logs, history and per-run summary tables
MERGEUpserts on the target's primary key (dq_key__c)Incremental runs. Rows deleted at source stay in the target
MERGE_UPSERT_DELETEUpserts and deletes. Every row needs _merge_record_type set to UPSERT or DELETEIncremental runs where source deletes must flow through
Try it live: delete DP-300006, change NA-100001's email, re-upload, and rerun under each mode. Under MERGE the deleted row survives; under MERGE_UPSERT_DELETE it's removed.

Keep these on screen

12 golden rules

  1. Lowercase every column name in the script. Object API names stay as shown.
  2. Read and write the same object type: DLO → DLO or DMO → DMO.
  3. Create the target DLO first, with fields that match the DataFrame.
  4. Rules in plain functions; the SDK only in main().
  5. Test before you spend: pytest → scan → run → deploy.
  6. Bump RULE_VERSION on every rule change.
  7. Never null the hash. Coalesce blanks to '' first.
  8. Never print PII. The logs DLO has no governance policies.
  9. Size it on purpose: --cpu-size CPU_L unless you've measured a need for more.
  10. Built-ins only. No UDFs, RDDs or SparkContext.
  11. It runs only through a batch data transform. Schedule it only with a credit owner.
  12. Promote with a data kit. Never rebuild by hand.

Talk track

What customers always ask

"Why not just do this in SQL?"

You can, for a few rules. Once you have dozens of regex rules across several objects, you'll want unit tests, versions and one place to change them.

"How many credits does it cost?"

Compute time × CU size, with a 60-second minimum per run. Measure on your volume, and always set --cpu-size.

"Can it break identity resolution?"

It improves it: 18,000 correct profiles instead of 21,755 with 1,045 wrong merges.

"What if the rules are wrong?"

Change one function and bump the version. The tests show the effect before you redeploy, and the hash proves the new rule reached every row.

"Is our data safe in logs?"

Only if the script never prints record values. The logs DLO has no governance policies, so log counts and step names only.

"How does this get to production?"

A DevOps data kit. Add the batch data transform, and the code extension comes with it.

Before the session

Clear the day-of blockers early

In the org

  • Data 360 provisioned, and Code Extension enabled in Feature Manager
  • The driver has Data Cloud Architect, plus CRUD on Data Custom Code Procedure Definitions
  • The org is not BYOK (code extension isn't supported there)
  • Someone owns the credits and decides who can schedule

On the driver's laptop

  • Python 3.11 and Azul Zulu OpenJDK 17
  • Salesforce CLI ≥ 2.130.9 with @salesforce/plugin-data-code-extension
  • Docker running, for CLI deploy. If the corporate laptop blocks it, use the UI zip upload instead
#1 blocker: a missing permission set or the Code Extension feature not enabled. #2: a laptop that can't run Docker or install Python 3.11. Check both before the session.
